# 發票機串接架構設計（WinPOS WP-560 二聯式發票機）

> 目標：把現有「每日結帳手動抄發票號碼」升級為**系統直接驅動實體發票機列印統一發票**，並在收款當下自動記下發票號、結帳起訖號自動帶出。
> 決策（2026-07-21 拍板）：**實體二聯式紙本發票**（不走電子發票）＋**本地列印代理**橋接＋號碼**後端計數**＋收款當下開票＋二聯**選填統編**。
> 狀態：**架構已定，待硬體到位進 PoC**。使用者採購舊發票機＋RS-232轉USB＋二聯練習紙捲；下一步 P1＝本地代理 + 列印對位 PoC（見第 6 節）。

## 0. 現況（2026-07 快照）

- 系統**本身不開發票**。實體發票機印統一發票，店員在**每日結帳**（`DailySettlementPage`）手動輸入發票起訖號、作廢號、作廢金額。
- 系統僅收下號碼供報表：`dailySettlements` 存 `invoiceSegments`(多段起訖) / `invoiceStartNumber` / `invoiceLastNumber` / `invoiceVoidNumbers` / `voidInvoiceAmount`；產「月銷售紀錄」與「發票明細表」（仿二聯式收銀機統一發票明細表）。
- 收款點（未來要掛開票）目前都已呼叫 `recordTransaction()` 記營收：
  | 流程 | 收款確認點（員工端） | 交易 type |
  |---|---|---|
  | 入場 | `CheckinPage` 掃碼→確認入場／電話入場／已付費放行 | `checkin` |

  | 課程 | 待辦頁待收款確認（現金/轉帳）／報名現金 | `course` |
  | 定期票 | `POST /passes`／入場 buy_pass | `pass` |

## 1. 硬體：WinPOS WP-560（已查證可串）

- **機型**：WinPOS WP-560 **二聯式發票印表機**（配件性質，需搭主機/PC 驅動；非獨立收銀機）。
- **列印方式**：**9 針點陣撞擊式**（impact，非熱感）→ 適合二聯式複寫紙；速度約 3 行/秒。
- **介面**：**RS-232 序列埠** ＋ 並列埠。現代 PC 需 **USB-to-serial 轉接線**。
- **指令集**：**ESC/POS、TP-3688、HPC-2000、IPT-2009 多模式，用 DIP 開關切換** → 走 **ESC/POS（公開標準指令集）** 即可程式驅動（關鍵，不是只能手按的機型）。
- **能力**：二聯式（存根聯＋收執聯）同時列印、證明聯單獨列印、自動定位/裁切、缺紙/卡紙/定位錯誤警示、可接錢櫃、內建中文字庫（16×9 點陣）。
- 參考：momo `i_code=8386654`、大山事務機 `dasan.com.tw/product/wp-560/`、百揚 Ushow POS、RS232 線材 winsmaker（WP520/WP560/WP103S 專用）。

## 2. 關鍵現實：紙本發票的「號碼」怎麼管

- 二聯式紙本統一發票的**號碼是預先印在財政部配號的專用發票紙捲上**。WP-560 只做「**自動定位**」：把日期/金額/品項印到當前那張預印號碼的發票上，**機器本身不產生號碼**。
- 因此號碼由**系統計數**管理：
  1. 店員**換紙捲/換期別**時，把該捲**起始發票號**輸入系統一次（含字軌）。
  2. 每成功列印一張 → 系統把號碼記到該筆交易、**計數 +1**。
  3. **作廢**（打錯）→ 該號標作廢、跳號。
  4. 每日結帳起訖號**自動帶出**（取代現手動抄號）；月銷售/發票明細自動產生。
- ⚠️ 風險：系統計數與實體紙捲**必須對齊**。要有「目前號碼」顯示 + 換捲重設 + 對不上時可手動校正的機制。

## 3. 橋接：RS-232 → 網頁員工端 → **決定走「本地列印代理」（方案 B）**

員工端是網頁（Firebase Hosting），無法直接驅動序列裝置。**已拍板走方案 B 本地代理**（2026-07-21）。

| 方案 | 做法 | 決定 |
|---|---|---|
| A. 瀏覽器 Web Serial API | Chrome 直接開序列埠送 ESC/POS | ❌ 不採用 |
| **B. 本地列印代理程式** | 櫃檯 PC 裝小程式開 COM 埠、開 `localhost` HTTP 給網頁呼叫、翻譯成 ESC/POS | ✅ **採用** |

**硬體規劃（使用者）**：買一台**舊發票機**測試、**RS-232 轉 USB** 接櫃檯電腦、已有**二聯式練習紙捲**。

### 3.1 本地代理設計
- **技術**：Node.js（與後端同語言）＋ `serialport`（開 COM 埠、送 bytes）＋ `express`（開 `http://localhost:<PORT>`）。
- **平台：Windows**（櫃檯電腦）→ 打包成 Windows 執行檔（`pkg`）或裝成 **Windows 服務**（如 `node-windows`/nssm）開機自啟；COM 埠走 Windows 命名（`COM3`…，RS-232轉USB 會配一個 COM 編號，裝置管理員可查）。
- **端點**：
  - `POST http://localhost:<PORT>/print` — 收發票內容 → 組 ESC/POS → 寫入 COM 埠 → 回 `{ ok, error? }`
  - `GET  /status` — 連線/缺紙/COM 埠狀態
  - `POST /void`（如機型支援）／或作廢僅由後端標號碼
- **呼叫方**：員工端網頁（同一台櫃檯 Chrome）`fetch('http://localhost:<PORT>/print', …)`。
- **⚠️ 瀏覽器限制（要處理）**：HTTPS 頁（`staff.redrocktaiwan.com`）呼叫 `http://localhost`——localhost 是安全內容例外**不會被 mixed-content 擋**，但新版 Chrome 的 **Private Network Access** 會發 preflight，代理需回應 `Access-Control-Allow-Private-Network: true` ＋ CORS 允許該來源。此為已知可解的細節，代理端設定即可。
- **設定**：COM 埠編號、baud rate、DIP 對應的發票定位參數，放代理的設定檔（每館櫃檯各自設）。
- 列印介面抽象見 5.1（`InvoicePrinter` adapter `localagent`）。

## 4. UI 整合（二聯式較單純）

- 二聯式＝**B2C，無載具/捐贈** → 收款確認流程乾淨。
- 做一個共用流程 **「收款確認 → 送印 → 記號碼」**，四頁共用：

  `入場/租借/銷售/課程 收款確認` → 組發票內容（日期＋金額＋品項；租借**只租金不含押金**；**選填統編**） → 送 ESC/POS 列印 → WP-560 印在當前發票 → 系統記該張號碼＋計數 +1。

- **統編（選填）**：二聯式**有時客人也要印統編**（報帳） → 收款確認的共用元件加**選填統編欄**（8 碼），有填就印在發票上、存進 `invoices.buyerTaxId`。多數 B2C 留空。（真正 B2B 三聯式格式日後要再擴充。）
- **作廢/退費連動**：現有取消/退費流程 → 能作廢就作廢、否則直接退費（不折讓，詳見第 4.1 節）。
- **錢櫃驅動**：WP-560 有**錢櫃輸出埠**（錢櫃接發票機、非接 PC），代理用 ESC/POS `ESC p`（`0x1B 0x70`）開櫃。`InvoiceCheckout` **現金收款才帶開櫃**（電子/轉帳不開）；現金退費、每日結帳點鈔可另給「開錢櫃」鈕。代理端點加 `POST /open-drawer` 或 `/print { openDrawer:true }`。
  - 🚨 **硬體安全警告（2026-07-31，WP-560 說明書原文）**：「**注意：請勿使用 TP-3688 相容錢櫃，否則將造成印表機及錢櫃嚴重毀損**」。TP-3688 是這台印表機**出廠預設**的協定（本案已撥 DIP2#3 從 ON→OFF 切到 ESC/POS 相容模式，見 §5.5）；TP-3688 與 ESC/POS 是兩套不同電路訊號規格（觸發電壓/極性/脈衝方式不同），**接錯類型的錢櫃有實際燒毀硬體的風險，不可用試的**（跟純軟體指令試錯的風險層級不同）。**接任何錢櫃前，務必先確認該錢櫃是「標準 ESC/POS(Epson) 相容」而非「TP-3688 相容」**（多半要查該錢櫃/該收銀機的原廠說明書或問經銷商）。
  - ✅ **WP-520（同系列機型）錢櫃接腳規格確認（依說明書）**：**RJ12（6P6C，6 線）**——外殼地／錢箱輸出1／微動開關（偵測錢櫃開闔狀態）／電源 +24V／錢箱輸出2／邏輯地。這是業界通用的「Epson 相容型」標準錢櫃接法。
  - 📌 **實務決定：市面上只找得到 RJ11（4線）錢櫃 → 直接採用**：RJ11 插頭可physically插入 RJ12 插座（形狀相容，只是少接 2 條線）——跟 ACCUPOS「接頭形狀完全不同」是不同等級的狀況，屬「軟性風險」（頂多缺少微動開關的錢櫃開闔偵測功能、或基本開櫃也失敗，實測便知），**非**燒毀硬體等級的風險。且本案**只需要 `ESC p` 觸發彈開、不需要微動開關的偵測回報**，即使 RJ11 少接的剛好是那 2 條線也不影響需求。**結論：買 RJ11 錢櫃即可，正式接線時實測開櫃功能是否正常**。
  - ✅（2026-07-31 已釐清，結論＝不接）**ACCUPOS A600 附贈錢櫃確認不相容、不接**：實際檢查兩邊接頭——WP-560/WP-520 錢櫃孔＝標準 RJ12 模組化方孔（6 pin，見上）；ACCUPOS A600 錢櫃線＝**三線（黑/綠/紅）、方形三孔接頭**，3 條線本來就裝不下上述 6 個獨立訊號、接頭形狀也完全不同，**物理上插不進去**。加上 TP-3688 混用警告、兩品牌同屬中文收銀機生態系（撞型號風險高），**結論：不接、不做轉接線嘗試**。正式上線改買一台**標準 RJ12、ESC/POS(Epson) 相容**的獨立錢櫃即可（市面普遍、便宜）；ACCUPOS A600 若仍要用，維持原廠主機+印表機+錢櫃配對使用。
- **補印**：交易/會員紀錄旁加「補印發票」（重印證明聯，不佔新號）。
- **開票失敗退路**：款已收、列印失敗（缺紙/斷線）→ 進「**待開立佇列**」，不卡收款；UI 顯示「發票待補印」，排除後補印。

## 4.1 退費 → 作廢發票＋退款一律綁在一起做，不分開處理（2026-07-21 定案；**2026-08-03 修正簡化**）

> 使用者現行做法：退費一律**直接退錢**、不開折讓證明單。故本專案**不做折讓模組**（`allowances`、折讓單列印都不做），大幅縮小範圍。

> ⚠️ **2026-08-03 修正**：原規劃「同期別+全額+收得回發票兩聯→作廢；跨期/部分/收不回→直接退費、原發票不動」的雙軌判斷**不符合實際做法**，使用者更正：**「退貨」永遠是單一動作＝作廢原發票的全部金額＋全額退款給會員，兩件事一起做，沒有例外、不分同期跨期/全額部分**——不會出現「發票留著沒作廢、但錢已經退了一部分」這種中間狀態。若會員之後仍需要付款（不論是修正後的金額或全新消費），一律視為**全新一筆交易**：會員重新匯款 → 店家開立**一張全新的發票**，與被作廢的舊發票無關聯。這樣每一張「未作廢」的發票永遠代表「這筆錢目前真的收在店裡、還沒退」，帳務對照上不會有中間模糊狀態。

| 動作 | 系統處理 |
|---|---|
| **退貨（唯一路徑，不分同期/跨期/全額/部分）** | 作廢該發票號的**全部金額**、**跳號**、自動帶進結帳「作廢號碼/金額」（＝現手動記作廢自動化）；**同時全額退款**給會員（現有負向沖銷退錢邏輯）；`invoices.status='void'` |
| **會員之後仍需付款** | 視為全新交易——會員重新匯款，店家開立**一張全新發票**（新號碼、新金額），與被作廢的舊發票無關聯 |

- 統一發票期別＝雙月（7-8月、9-10月…）；**本政策刻意不受此限制——即使是跨期的舊發票也一律作廢**（見下方財稅提醒）。
- **接現有退費流程**（錢的退費已由負向沖銷處理，此為加的發票層）：取消入場／課程退費／試上取消／比賽·租借退費，一律作廢原發票＋全額退款（不論金額是否全額、是否跨期）。
- **作廢發票（退貨）直接記進當日結帳加減項**（2026-08-03 補）：退款金額以「－」項記進**作廢當天**的日結帳，沿用現行過渡版 §9（`invoiceService.js`）已經在用的「-發票作廢」對稱沖銷機制，正式串接印表機後**維持同一套做法**，不用另外設計新機制。

⚠️ **財稅提醒**（使用者知悉並選擇維持簡單一致的做法，非違法）：財政部規定嚴格來說「作廢」通常限**開立當期內**（跨期、尤其已申報的發票原則上不能簡單作廢，須另走折讓證明單）。本專案為求帳務簡單一致（每張未作廢發票＝店裡目前真的收著的錢，沒有中間狀態），**刻意不做期別區分、一律作廢**——這代表跨期作廢在稅務申報上可能需要會計額外調整處理，**由使用者/會計自行承擔與處理，系統不另外攔阻**。**✅ 做「退費/作廢報表」**（給會計作帳）：每筆列 原發票號/金額/日期/關聯訂單，**尤其標出跨期作廢的筆數**，供會計月結/申報時對照調整，可匯出 CSV/Excel。

### 4.1.2 📋 未來政策（2026-08-03 提出，**待發票機正式串接後才實施，現在不動**）——按鈕命名、二次確認、線上支付退款

> 討論起因：正式列印上線後，「開立發票」按下去、已開立的訂單畫面應該長什麼樣？延續 §4.1（2026-08-03 修正版：作廢＋退款一律綁在一起做）一併定案。

- **按鈕命名改「退貨」（取代目前過渡版的「作廢發票」）**：既然退費永遠是「作廢＋退款」綁在一起做的單一動作，用「退貨」當顧客/店員看到的動作名稱更貼切（比「作廢」更完整涵蓋「錢也退了」這件事）。**不需要分支邏輯**——按下退貨永遠做同一件事：作廢原發票全額＋全額退款，沒有店員需要判斷或選擇的分岔。
- **二次確認 modal 統一文案**（不再需要區分兩種結果，因為只有一種結果）：「將作廢發票 {號碼}（NT${金額}）並全額退款給會員，此發票號碼作廢後**即不再使用**（跳號）；若會員之後仍需付款，開立新發票時會使用下一個全新號碼。」**號碼一經開立，即使日後作廢，也永遠不重複使用**——與 §4.1 的「跳號」原則一致，避免發票號碼被誤解成可重複用。過渡版已有的「開立後顯示摘要＋二次確認才執行」UX 模式（`InvoiceModal.jsx` 現行的內嵌確認區塊，取消/確定兩鍵）沿用即可，正式版只需把訊息文案改成上述。
- **線上支付（LinePay/街口/台灣Pay）退貨＝目前規劃不會自動退款**：`payment-integration-plan.md` 的金流 adapter `refund()` 明確列為 Phase 4「之後做」、尚未開始（連 Phase 1-3 的金鑰/串接都還沒上線）。故無論原本用哪種方式付款，「退貨」在**現有規劃範圍內**都只會：①作廢發票＋跳號 ②系統記帳（負向沖銷全額退費），**不會**呼叫金流閘道把錢自動吐回顧客的 LinePay/街口帳戶——這點與系統現行所有退費（入場/課程/比賽/租借）的處理方式一致，全部是「系統記帳、實際退款人工處理」。
  - **拍板：維持人工退款**（不在發票機/退貨這波做線上自動退款）。理由：範圍最小、與現行全站退費機制一致；之後金流 API 真正上線，若要做「線上支付自動退款」屬於**另一塊獨立工程**（金鑰/簽章/callback 皆要重做一次），屆時另外評估排期，不綁在這次發票機專案裡。
  - 若之後真的要做，待辦頁可考慮加一顆「已完成退款」的手動核對鍵（供店員標記已經匯款/操作完退款），但這也是屬於「之後再說」，目前不動。

### 4.1.3 📋 未來政策（2026-08-03 提出，**待發票機正式串接後才實施，現在不動**）——既有取消/退費動作自動連動作廢發票，不分開按

> 使用者拍板：**取消入場（及其他訂單類型既有的取消/退費動作）不需要額外去發票查詢頁按一次「退貨」——取消動作本身應該自動連動作廢對應發票＋全額退款，一個動作內完成。**

- **原理**：延續 §4.1「退貨＝作廢＋退款一律綁在一起做」的精神，再往前推一步——不只是「退貨」這個動作內部不分兩條路，連「觸發退貨的入口」也不該分成兩個按鈕（先取消訂單、再另外去作廢發票）。分兩步容易漏做（訂單取消了、卻忘記去作廢發票），造成「錢已經退了但發票還留著」的中間狀態，正是 §4.1 想避免的。
- **實作方式**：各既有取消/退費流程（比照 §5.3 收款點接線表：入場 `cancelCheckIn`／課程退費／比賽退費／租借退費／體驗取消／商品銷售 `SalesPage.jsx` 現有 `returnSale`）執行時，**查詢是否有對應的已開立發票**（`invoices` 依 `relatedType`+`relatedId` 對應該筆訂單、`status='issued'`）——有的話自動套用 §4.1 的「作廢＋全額退款」；退款本身沿用各流程既有的負向沖銷邏輯（如入場已經有的 `cancelCheckIn` 回沖機制，見前述問答），作廢只是**額外**連動發票層，不取代原本各自的退費/回沖邏輯。
- **冪等處理**：發票已經是 `void` 狀態（如已被手動作廢過）→ 跳過不重複處理。
- **§4.1.1/§5.2.1「輸入發票號碼查詢＋退貨」的定位調整為補救/例外用途**：日常取消訂單一律走該訂單類型**既有的取消/退費動作**（自動連動作廢）；「輸入號碼查詢」的路徑保留給例外情況（如發票關聯的原始訂單已被刪除、連動失敗需要手動核對），不是常態操作路徑。

### 5.2.1 📋 未來政策（2026-08-03 提出，**待發票機正式串接後才實施，現在不動**）——發票查詢頁

> 討論起因：「開立發票按下後，號碼會顯示在哪、怎麼查詢？」——除了 §5.1/§4.1.1 已規劃的「列印當下顯示」「已知號碼查訂單」兩種情境，使用者拍板**再加一個獨立的發票查詢頁**，補上「不知道號碼、只知道會員/日期，想反查」的情境。

- **篩選條件**：日期區間、館別、狀態（已開立/已作廢）、關聯類型（入場/租借/商品/課程/定期票）、**會員姓名**（故 §5.2 schema 補 `memberId`/`memberName` 冗餘欄位，避免每筆都要反查 `relatedId` 才能顯示/搜尋姓名）。
- **列表顯示**：發票號碼、日期、館別、品項/金額、狀態、關聯訂單類型＋**可點擊連結跳回原始訂單**（如課程報名詳細資料）。
- **退貨動作可直接在此頁執行**：不用先找到訂單才能退貨——查詢頁本身就是 §4.1.1「輸入發票號碼、系統自動查出品項/金額」的天然入口，也可以直接從列表點某一筆執行退貨（作廢＋全額退款，見 §4.1），不必侷限在原訂單的詳細頁面裡才能操作。
- **權限（2026-08-03 依使用者拍板修正為三段式，非單一頁面權限）**：
  - **一般瀏覽/篩選清單**（依日期區間/館別/狀態/會員姓名瀏覽所有發票）→ 比照現行「下載明細/財務類頁面限管理員」慣例（`requireManager`，僅 `super_admin`/`gym_manager`；**值班 operator 不可用**——這塊接近財務稽核用途，開放給值班反而讓任何在班的人都能看到全館歷史交易明細，範圍過大）。
  - **輸入發票號碼查單筆＋執行退貨**（§4.1.1 的「已知號碼→查出→確認退貨」流程，非瀏覽清單）→ **開放給值班 operator**（`requireManagerOrStation`，管理員或值班皆可）——這是即時櫃檯操作（客人拿發票來要退貨），不應該卡管理員才能處理。
  - **號碼計數器校正**（見下）→ 同樣**開放給值班 operator**（`requireManagerOrStation`）——卡紙/跳號多半是值班當下發現，應能就地處理，不用等管理員。
- **號碼計數器校正（2026-08-03 追加）**：若 `invoiceState.currentNumber`（系統預期的下一號）跟實際紙本印出的號碼不明原因對不上（如卡紙浪費一張、印表機重印但計數沒扣回），頁面**頂部**顯示「本館目前發票號碼：{字軌}{號碼}」＋一顆「校正號碼」按鈕（值班 operator 或管理員皆可見）——開一個小 modal 輸入正確號碼＋選填備註原因，送出後更新 `invoiceState.currentNumber`，並留稽核紀錄（改的人/時間/原值→新值/原因，比照現行其他手動覆蓋欄位如 `receivedAmountOverride` 的做法）。**換捲重設**與**中途校正**是同一個動作、只是觸發時機不同，共用同一顆按鈕/同一個 modal，不必分開做兩套。
  - **只處理「計數器」層級的錯位**（下一個要配發的號碼跟現實脫鉤）；**不需要**額外做「編輯某一筆已開立發票的號碼」功能——正式系統下號碼是後端在列印當下權威配發（非店員手動輸入，見 §5.1/§2），單筆 `invoices.number` 必然等於配發當下的 `invoiceState.currentNumber`，理論上不會出現「某一筆的號碼本身記錯」這種情況（跟目前仍需店員手動輸入字軌+號碼的過渡版 §9 不同）。
- **前端呈現上的影響**：值班 operator 開此頁只看得到「輸入號碼查詢＋退貨」與「目前號碼／校正」兩塊；一般瀏覽/篩選清單的區塊只有管理員登入才顯示（比照本專案「前端隱藏非管理員按鈕＋後端 gate 強制」的既有慣例）。

### 5.3.2 📋 未來政策（2026-08-03 提出，**待發票機正式串接後才實施，現在不動**）——分期付款開票時機

> 使用者拍板：**分期付款訂單（課程/定期票/續約分期）不比照§7「每次收款確認就開票」——要等到最後一期全部付清、整筆分期結清後，才開立一張發票（金額＝分期總額，不是單一期的金額）。**

- **與 §7「開票時機＝各流程收款確認當下」的例外關係**：一般（一次付清）訂單維持原規則——收款確認當下就開票。**分期訂單是唯一的例外**：首期、中間各期收款時**都不開票**，只有在**最後一期付清、分期計畫結清**的那一刻，才開立**一張**發票（金額為分期總額）。
- **理由**：分期本質上仍是「同一筆消費」（一門課、一張票），若每期各開一張，會產生多張零碎小額發票，也跟顧客感受的「一次消費、分期付款」不符；等全部付清再開一張完整金額的發票，同時呼應 §4.1 剛定案的精神（一張發票＝一筆完整、金額對得上的交易，不留中間狀態）。
- **尚未付清就取消/退費的分期計畫（如中途違約、繳到一半不繼續）**：因為根本還沒開過票（沒有發票號碼可作廢），**不涉及 §4.1 的「作廢」動作**——退的是「已收的部分期款」，直接走現有負向沖銷退錢邏輯即可，系統帳上也不會出現一張「開了又要處理」的發票。
- **已付清、發票已開立後才取消/退費**：走一般 §4.1 規則（退貨＝作廢該發票全額＋全額退款一起做，號碼跳號不重複使用）。
- **列印前（分期期間）收的款項，依付款情境分兩種處理**（2026-08-03 定案，取代先前「待決定」）——關鍵區分＝**是否現場收款（現金）**：
  - **定期票／續約分期（現場收款）**：每期實際收款的那一天，該筆金額就當天以「＋」項記進日結帳（比照現行過渡版 `invoiceService.js` 的「+發票開立」記帳機制，差別是此時記的是「當期收款」而非「發票開立」，因為此時還沒真的開票）。**最後一期付清、正式開立發票當天**：記「+發票開立 {分期總額}」，**同時另外記一筆「－{先前各期已記過的加減項總和}」**——兩者淨額剛好等於「當天實收的最後一期金額」，發票雖顯示總額，但不會讓當天現金對帳灌水，現金才會對得起來。
  - **課程分期（一律轉帳，非現場收款）**：因為分期各期付款都不是現場現金（會員自行匯款、走既有 transferRecords/待收款確認機制記帳追蹤），**分期進行中，各期入帳完全不登記進日結帳加減項表**（不需要也不應該重複進到現金對帳表）。等**最後一期付清、開立發票當天**，才在日結帳加減項記**一筆「－」項，純作說明用途**（如「課程分期發票開立 NT$X（轉帳，非現金）」）——這筆「－」不是要扣現金，而是刻意抵銷「開立發票」預設會產生的「+」記帳效果（因為這筆錢從沒經過現場現金），同時仍留一筆「今天有開這張發票」的可追溯紀錄，供日後對帳/查核。

## 5.4 SDK / 指令手冊現況（2026-07-21 查證）

- WP-560 走 **ESC/POS 標準指令集**（另可 DIP 切 TP-3688/HPC-2000/IPT-2009）。ESC/POS 是**公開標準**（`ESC` 0x1B / `GS` 0x1D 起始）→ **基本列印（文字、金額、對齊、切紙、開錢櫃）可直接依公開 ESC/POS 手冊實作**，不需原廠 SDK。
- 但**沒有在網路上找到 WP-560 官方完整 SDK / 程式手冊**。社群有用 ESC/POS 驅動同系列 WinPOS 出據機的實例（Delphi × ESC/POS × WP-T810、POS 列印電子發票證明聯）可參考做法。
- **定位可自己做（靠試印校正，非必須原廠規格）**：二聯式發票的定位＝**游標控制**（換行往下 N 行、`ESC $` 絕對水平位置/空格右移 N 字）。9 針點陣固定字距，位置＝(行, 欄) 好算；發票格式財政部標準、紙捲尺寸固定 → 每欄位相對表頭的偏移量**固定、量一次寫死**；機器「自動定位」負責對齊每張表單起點，我方只管表單內欄位偏移。用**練習紙捲印→看歪→調偏移→再印**收斂即可。
- **結論**：基本列印＋定位**皆可自幹**（公開 ESC/POS + 試印校正）。經銷商的**定位範例/DIP 設定只是加速**（省初始偏移與 DIP 模式試錯），不是動工必要條件。
- ⚠️ 真正的風險點：舊機的**自動定位感測器**若異常/紙捲無定位標記，表頭對齊會較麻煩（買到機器一試即知）——這是 P1 PoC 要先確認的。

## 5.5 P1 PoC 實測結果（2026-07-31，舊機＋USB轉RS232＋練習紙捲，已過最大技術風險點）

> 用 `scratchpad/printer-test/`（Node + `serialport`，throwaway、不進版控）直接送 raw ESC/POS bytes 到序列埠測試，逐步排查後**確認可穩定列印中文**。以下為實測得出的關鍵設定，日後寫正式本地代理程式**直接套用即可、不用重踩**。

- ✅ **實體連線**：USB-RS232 轉接線裝置為 `/dev/cu.usbserial-DU0ERYQM`（Windows 上會是 COM 埠），**baud 9600、8 data bits、no parity、1 stop bit**。序列埠開啟/寫入本身完全正常、無需特殊設定。
- ✅ **DIP2 開關第 3 顆（機器底部）須撥到 OFF**：出廠預設是 TP-3688 專屬指令集，這台不撥開關的話**完全不理會 ESC/POS 指令、連進紙都沒反應**；撥到 OFF 後才會開始解讀 ESC/POS bytes（可聽到馬達進紙聲音當作已生效的訊號）。DIP1/DIP2 兩組開關都在機身底部（斷電後翻過來看，開關很小可用原子筆尖撥動）。
- ⚠️ **面板紅燈是這台正常狀態、不是錯誤燈號**——先前排查了紙張感應器/紙蓋/存根聯回收捲軸繞法都正常，最後才確認「開機從頭到尾都是紅燈」對這台機器來說是正常現象，**不要拿它當診斷依據**、以實際列印結果為準。
- 🐞 **這台的 ESC/POS 指令集是有限子集，以下指令會產生亂碼、確認不支援，勿使用**：
  - `ESC G n`（雙重列印）、`ESC E n`（加粗）——送出後**不會被當指令消化**，`ESC` 位元組被忽略、後面的英文字母（`G`/`E`）被當成一般文字印出（且會印成**全形**字元，如「Ｇ」「Ｅ」），造成亂碼。
  - `FS &` / `FS .`（Kanji 模式切換）——同樣不支援，送出後在該行前後產生亂碼字元。
- ✅ **中文列印做法（已驗證乾淨可用）**：**完全不需要任何模式切換指令**——`ESC @`（初始化）之後，直接把中文字串用 **Big5** 編碼（`iconv-lite` 的 `iconv.encode(str, 'big5')`）送過去即可正確印出中文，中英文混排也沒問題。**切勿用 `Buffer.from(str)`**（Node 預設 UTF-8）送含中文的字串，兩種編碼對不上會印出亂碼——這是這次測試踩到的第一個雷，錯誤出在測試腳本本身、不是印表機的問題。
- ✅ **`GS ! n`（字體放大，如 `0x11`＝寬高各 2 倍）指令有效**：這台的色帶（IR-71 相容）已偏舊、正常大小印出的字偏淡但**堪讀**（使用者實測「還可以」）；如需加強清晰度，放大字體（`GS !`）是目前唯一驗證有效的加強手段（`ESC G`/`ESC E` 雙重列印/加粗都不支援，見上）。**建議日後正式上線前更換一捲新的 IR-71 相容色帶**（網路上幾百元可買到），現況已堪用、非阻塞項。
- ✅ **紙張機構確認正常**：紙蓋扣緊、無需額外壓桿、進紙定位正常、存根聯（副聯）回收捲軸繞接方式也正常——這些先前擔心的「二手機物理故障」皆已排除。
- 📌 **正式代理程式（P1 之後的 P3/P4）撰寫時的具體套用**：初始化只送 `ESC @`；中文/英數混合字串一律先 `iconv.encode(str,'big5')` 再送位元組（勿用預設 UTF-8）；不要用 `ESC G`/`ESC E`/`FS &`/`FS .`；如需加粗視覺效果改用 `GS !`（字體放大）；換行/定位游標控制（`ESC $`／多個 `\n`）等基本指令未在本次測試範圍內驗證，等實際刻二聯式發票版面時再逐一試印校正。
- ✅ **重大發現：`0x0C`（ASCII Form Feed 換頁指令）＝自動對位＋裁切！**——一開始連續送兩次列印（中間只用 `\n\n\n\n` 分隔）**沒有**自動對位/裁切，一度以為要自己算行數校正；後來測手動進紙鍵**按著不放會自動停在下一張起點並裁切**（證實定位感測器硬體正常），改送 `0x0C` 這個標準換頁指令（非 ESC/POS 專屬、是最基本的 ASCII 控制字元）→ **印表機自動進紙、對位、裁切，跟手動按鍵行為一致**！這代表**不需要自己算換行行數校正定位**，每張發票內容印完後**直接送一個 `0x0C` 位元組**即可自動跳到下一張正確起點並裁切好——大幅簡化原本預期要做的「試印校正」工作。
- 📌 **正式代理程式套用**：每張發票列印流程＝`ESC @` 初始化 → 中文/英數內容（Big5 編碼）→ **`0x0C` 結尾** → 自動對位+裁切完成，下一張直接可印，不需手動管理行數/偏移。
