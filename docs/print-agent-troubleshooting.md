# 發票列印代理（local-print-agent）失效處理手冊

> 適用：新竹館／士林館櫃檯的 WP-560 發票機本地列印代理故障時的現場處置。
> 歷次真實事故與修復記錄見 CLAUDE.md 2026-08-15（續4~續11）、2026-08-06（續10/續11）各段。
> 架構設計見 `docs/invoice-integration-plan.md`；安裝步驟見 `local-print-agent/README.md`（新竹/一般機）與 `local-print-agent/win7/README.md`（士林 Win7 機）。

## 0. 架構速覽（30 秒讀懂誰負責什麼）

- **每台櫃檯電腦跑一個本地代理**（`http://localhost:3399`），純負責「驅動印表機列印＋開錢櫃」。
  - 新竹：現代 Node 版（`local-print-agent/` 根目錄，Windows 服務名 `RedRockPrintAgent`，node-windows 安裝）。
  - 士林主機（Win7）：PowerShell 序列埠橋接版（`local-print-agent/win7/`，NSSM 服務名同為 `RedRockPrintAgent`）。
  - 士林備用機（ASUS，Win11）：現代 Node 版，平時待命。
- **發票號碼完全不在代理上**——`gyms/{gymId}.invoiceState` 存雲端 Firestore、以館別為鍵，瀏覽器打 `staff.redrocktaiwan.com` → 後端配號 → 才叫本地代理列印。**換電腦不影響號碼接續**。
- **列印失敗不消耗號碼、不建立發票紀錄**（`POST /invoices/print-record` 只在列印成功後才被呼叫）——同一個開票入口可安全重試，不會跳號。

## 1. 第一原則：收款不被開票卡住

1. **收款動作照常完成**（入場/POS/租借/課程/比賽的收款流程與發票完全解耦）。
2. 當下**手寫紙本發票**給客人（撕紙捲上正確的下一張號碼手寫）。
3. 修好之後再處理系統面（見第 5 節收尾），或直接在同一個開票入口重試補印。

## 2. 快速診斷（照順序，多數狀況 3 分鐘內定位）

**Step 1：在那台電腦的瀏覽器直接開 `http://localhost:3399`**
（網址列直接打——這是頁面導覽、不受 CORS/PNA 限制，員工端網頁連不上時這裡常常是通的）

| 結果 | 判讀 | 下一步 |
|---|---|---|
| 打得開、測試頁「檢查連線狀態」`connected:true` | 代理與印表機都正常 → 問題在員工端網頁到代理之間 | 確認代理版本是 2026-08-15 之後（見 Step 4）；hard reload 員工端頁面 |
| 打得開、`connected:false` | 代理活著、序列埠層有問題 | 檢查印表機電源/線材/紙捲；重啟服務（Step 2）重開序列埠 |
| 打不開 | 代理行程沒在跑 | Step 2 |

**Step 2：重啟服務**
開始選單搜尋「服務」（`services.msc`）→ `RedRockPrintAgent` → 重新啟動 → 回 Step 1 驗證。

**Step 3：服務起不來 → 手動頂著，先恢復營業**
到 `local-print-agent` 資料夾（士林 Win7 是 `win7` 子資料夾）開命令視窗跑 `npm start`——看到啟動訊息即可開票。**該黑色視窗不可關閉**。服務層問題離峰再修（見第 3 節對照表）。

**Step 4：核對版本標記**
啟動訊息/`/status` 回應帶 `agentVersion`：
- 士林 Win7：`persistent-serial-daemon-2026-08-15`（常駐序列埠版）或 `pna-preflight-fix-2026-08-15`（回滾版，兩者皆可用）。更早的版本標記＝跑到舊檔案，要重新覆蓋檔案。
- 常駐版若行為異常，`.env` 設 `PERSISTENT_MODE=false` 可退回「每次請求重開埠」的舊行為（較慢但已驗證可靠）。

## 3. 常見病因對照表（全部是踩過的真實雷）

| 症狀 | 病因 | 解法 |
|---|---|---|
| 員工端顯示「無法連線到本機列印代理」，但 localhost 打得開 | ①代理版本太舊缺 PNA preflight header（Chrome 私有網路存取直接擋下請求）②前端逾時（舊版 3 秒 < 這批機器序列埠 6 秒回應） | 兩者皆已於 2026-08-15 修復——更新代理檔案到修復版＋員工端 hard reload 載新 bundle |
| 睡眠喚醒後突然失效 | 序列埠喚醒異常 → 代理行程崩潰 →（服務重啟時才暴露的）其他設定問題 | 重啟服務即復原；**根治＝該電腦電源選項設「從不睡眠」**（2026-08-15 士林事故的觸發點，兩種代理架構都建議關睡眠） |
| 服務啟動失敗、`service-stdout.log`/`service-stderr.log` 完全空白 | NSSM 設定壞值（node.exe 從未被啟動）。已知兩種：`Application` 路徑錯字（`node.js` → 正確是 `nodejs`）、`AppDirectory` 結尾多一個 `"` | **開全新命令視窗**跑 `nssm get RedRockPrintAgent Application` 與 `AppDirectory` 檢查，`nssm set RedRockPrintAgent <參數> "正確值"` 修正（路徑結尾不要帶反斜線）→ `nssm restart RedRockPrintAgent` |
| 反覆執行指令「結果都一樣沒變」 | 很可能是在同一個命令視窗往上捲、複製到**舊的畫面輸出**，不是重新執行的結果 | 每次驗證都**整個關閉命令視窗、開全新的**再執行（2026-08-15 事故曾因此在同一死結繞 3 輪） |
| 開錢箱按了「沒反應」 | 錢箱本來就是開著/沒閂緊——對已開的錢箱送脈衝看不出效果 | 先把錢箱確實關緊閂好再測（2026-08-06 假性失敗） |
| 覆蓋新檔案後行為沒變 | 檔案總管隱藏副檔名，重新命名附件時存成 `server.js.js` 雙副檔名 | 用命令列 `copy /y` 覆蓋，並用啟動訊息的版本標記確認真的換到新檔 |

## 4. 修不好時的兩條備援

### 4a. 士林：切 ASUS 備用機

號碼計數器綁館別不綁機器——ASUS 用士林帳號登入員工端即自動接續配號，**唯一要顧的是實體紙捲**：

- **方案一（建議）**：把紙捲直接從故障機移到 ASUS 的印表機——同一捲紙、號碼天生連續，不用動任何設定。
- **方案二**：ASUS 用自己的備用紙捲——**切換前務必**先到員工端「發票號碼管理」做換捲重設/校正（`PUT /invoices/state`），把 `currentNumber` 校正成 ASUS 那捲實際下一張的號碼。沒做這步＝系統配的號碼跟紙上印的對不起來。

### 4b. 整館暫時關閉發票列印開關

設定 → 場館與帳號 → 🖨️ 發票列印（**限 super_admin**）→ 關閉該館。五個流程（入場/POS/課程/比賽/租借）自動退回手動記帳版 modal（店員手寫發票＋手動輸入字軌/號碼記錄，走 `invoiceRecords` 集合）。修好後開回開關，並確認號碼銜接（停機期間手寫用掉的號碼要讓 `currentNumber` 跟上，用換捲校正）。

## 5. 事後收尾：手寫發票補登

停機期間手寫的每一張發票，修復後要補進系統，否則結帳的「發票總金額推算現金」會對不上：

1. **補建 `invoices` 紀錄**（比照 `POST /invoices/print-record` 寫入的欄位格式：`track`/`number`/`itemName`/`amount`/`paymentMethod`/`sourceType`/`refId`/`memberId`/`staffId`/`gymId`，`issuedAt` 用實際開立時間、另加 `backfillNote` 留稽核）——先例：2026-08-15 士林補登 CD78434919/78434920 兩筆。
2. **校正號碼計數器**：用正式的換捲重設功能（會留 `lastChange` 稽核）把 `currentNumber` 對齊紙捲實際下一張，**不要**直接手改 Firestore 欄位。
3. 若補登的是入場/補租這類「收入已由 checkIns/transactions 即時計算」的來源，**不要**另外寫結帳加減項（會重複計算，見 2026-08-15 續6/續7 的雙重計算修復）。

## 6. 預防清單（裝機/巡檢時過一遍）

- [ ] 電源選項「從不睡眠」（兩館所有發票機電腦）
- [ ] 服務 `RedRockPrintAgent` 開機自動啟動，**實際重開機測一次**（不要只看設定值）
- [ ] 啟動訊息版本標記＝目前應跑的版本
- [ ] `http://localhost:3399` 測試頁：連線狀態 + 測試列印 + 開錢櫃（錢箱先關緊）三項通過
- [ ] DIP 開關 2#3 OFF（Big5 中文模式）；面板紅燈為正常狀態，不是故障
